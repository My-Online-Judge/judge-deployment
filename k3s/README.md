# The stack on K3s

Kustomize: `base/` is what runs, `overlays/local` is k3d on a laptop (mock sandbox, images built by
`scripts/local-stack.sh build`), `overlays/vps` is the server. The migration plan is
`docs/superpowers/plans/2026-10-28-k3s-migration.md`; the spec it argues from is
`docs/superpowers/specs/2026-10-28-k3s-judge-pod-spec.md`.

```bash
scripts/k3d-up.sh up            # a K3s cluster `oj` in Docker; https://localhost:18443 and http://localhost:18080 are Traefik
scripts/local-stack.sh build    # the images (arm64 Macs: see the README's "Run it on one machine")
scripts/k3d-up.sh import        # load them into the cluster
kubectl apply -k k3s/platform   # once per cluster: cert-manager, installed by K3s's Helm controller
kubectl wait --for condition=established crd/certificates.cert-manager.io crd/issuers.cert-manager.io
kubectl apply -k k3s/overlays/local
k3s/scripts/env-to-secrets.sh   # the compose .env files as Secrets (pods wait for them; run it again after a change)
bash tests/k3s-render.test.sh   # every overlay renders and validates (OJ_DOCKER_CONTEXT=desktop-linux on a Mac)
bash tests/k3s-pki.test.sh      # certificates.yaml is what k3s/scripts/gen-certificates.sh makes from pki/identities.txt
scripts/k3d-up.sh down
```

The compose stack keeps 80, 443 and 9000, so both can run at once; `K3D_HTTPS_PORT` and `K3D_HTTP_PORT` change the
cluster's host ports (the script stops, naming the holder, when one is taken).

## Certificates

cert-manager signs one Certificate per identity of `pki/identities.txt` (`k3s/base/pki/certificates.yaml`, generated by
`k3s/scripts/gen-certificates.sh`; the CN, SANs, usages and PKCS8 key are those `pki/pki.sh` issues) and keeps each in the
Secret `tls-<identity>` (keys `tls.crt`, `tls.key`, `ca.crt`). A renewal happens 30 days ahead and makes a new key; a deleted
Secret is issued again within seconds. The signing CA is the Secret `oj-ca`:

- locally (`overlays/local`) cert-manager makes a throwaway root; to trust it in a browser:
  `kubectl -n oj get secret oj-ca -o jsonpath='{.data.tls\.crt}' | base64 -d > oj-local-ca.crt`
- on the server, `k3s/scripts/ca-from-pki.sh` loads the compose stack's CA (`pki/out/ca`) before the first apply, so
  everything that already trusts that CA keeps working through the cutover.

Traefik presents the identity `edge` (CN=edge) to the gateway and the portal, as Caddy does, so their allow-lists and the
gateway's client-address rule stay as they are.

## The data layer (`base/data`)

Three Postgres (identity-db, problem-db, submission-db), Kafka, Redis and MinIO are StatefulSets with a PVC each on the
`local-path` class, the same TLS-with-client-certificates as compose. `tests/k3s-data.test.sh` compares Kafka's environment
and the Postgres, Redis and MinIO command lines with `docker-compose.yml` value for value, so the two cannot drift before the
cutover. `postgres.yaml` and `init-scripts.yaml` are generated (`python3 k3s/scripts/gen_data.py postgres|init-scripts`) from
what compose runs and from `kafka/` and `minio/`; the test fails when a committed file differs.

- **Kafka is capped**: heap `-Xmx512M -Xms512M`, 512Mi requested, 1Gi limit.
- **Secrets**: `k3s/scripts/env-to-secrets.sh` turns the `.env*` files into the Secrets the pods read (`--dry-run` lists names and
  keys). MinIO's root account goes only to MinIO and `minio-init`.
- **Init Jobs** `kafka-init` (ACLs, `kafka/acls.sh`) and `minio-init` (bucket, policies, users) retry until their service
  answers and are removed ten minutes after they finish, so the next `kubectl apply` runs them again. To run one sooner, or
  after changing its script, delete it first (`kubectl -n oj delete job kafka-init minio-init`): a Job's spec cannot change.
- **Every pod is non-root** with the `RuntimeDefault` seccomp profile and no capabilities, so the namespace's `restricted` Pod
  Security warning stays quiet. A volume first written as root (an earlier version of the pod) must be deleted, not reused.
- `enableServiceLinks: false` everywhere: a Service named `kafka` would put `KAFKA_PORT` into Kafka's environment, and the broker
  reads every `KAFKA_*` variable as configuration. Service `kafka` also publishes not-ready addresses: the broker's controller
  quorum voter is `kafka:9093` and it is not Ready until it has joined.

## Services, edge and network (`base/services`, `base/edge`, `base/network`)

identity-service, problem-service, submission-service and api-gateway (`services/java.yaml`, generated by
`k3s/scripts/gen_services.py java`), the portal and Jaeger are Deployments over mutual TLS with the identity's own certificate.
`tests/k3s-services.test.sh` compares each service's environment with `docker-compose.yml`'s, the generated files with their
generators, and Traefik's headers and body limits with `edge/Caddyfile`'s. Differences from compose, on purpose:

- The JVMs get `-XX:MaxRAMPercentage=50.0 -XX:+UseSerialGC` and a memory limit (1Gi, the gateway 768Mi); a JVM start is CPU-bound,
  so each asks for 250m of CPU.
- A read-only root filesystem with `/tmp` as an emptyDir; non-root, `RuntimeDefault` seccomp, no capabilities, everywhere.
- The portal's nginx (uid 101) binds 443: the pod sets the safe sysctl `net.ipv4.ip_unprivileged_port_start=0` that Docker
  sets for a container.
- submission-service is replaced (`Recreate`), not rolled: its pending runs live in its memory.
- Traefik is the edge. It presents the identity `edge` (CN=edge) to the gateway and the portal, as Caddy does; `http` redirects to
  `https`; `/api/v1/problems` may carry 56 MiB, the rest of `/api` 1 MB. The browser-facing certificate is the Secret `edge-tls`:
  `overlays/local` signs one for `localhost` with its throwaway CA; the server's is Let's Encrypt (Task 10).
- **NetworkPolicies**: ingress is denied unless a policy allows it (`network/policies.yaml`): each store is reached by its own
  service, the services by the gateway, the gateway and the portal by Traefik. The test fails when a Service port has no allow
  rule (the actuators' 8081, for Prometheus, come with the observability task).
- The consoles are not Services: `kubectl -n oj port-forward pod/minio-0 9001`, `kubectl -n oj port-forward deploy/jaeger 16686`.

Locally the images are the ones `scripts/local-stack.sh build` made, loaded by `scripts/k3d-up.sh import`. Trust the local CA
with `kubectl -n oj get secret oj-ca -o jsonpath='{.data.tls\.crt}' | base64 -d > oj-local-ca.crt` and use it as
`curl --cacert oj-local-ca.crt https://localhost:18443/api/v1/languages`.

## What cannot be done on a laptop

The real qduoj sandbox is amd64 and needs the Linux host's kernel, so locally the Judge Pod runs the mock. Left for the
server (the checklist grows as the plan's tasks land):

- Task 6, sizing the sandbox's memory and CPU with real judgements (a+b, a heavy compile, a time-limit overrun, an
  out-of-memory kill, `kubectl delete pod` in the middle of a 10 s C++ judgement).
- Task 10, the cutover from compose.
