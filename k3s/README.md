# The stack on K3s

Kustomize: `base/` is what runs, `overlays/local` is k3d on a laptop (mock sandbox, images built by
`scripts/local-stack.sh build`), `overlays/vps` is the server. The migration plan is
`docs/superpowers/plans/2026-10-28-k3s-migration.md`; the spec it argues from is
`docs/superpowers/specs/2026-10-28-k3s-judge-pod-spec.md`.

```bash
scripts/k3d-up.sh up            # a K3s cluster `oj` in Docker; https://localhost:18443 and http://localhost:18080 are Traefik
scripts/local-stack.sh build    # the images (arm64 Macs: see the README's "Run it on one machine")
scripts/k3d-up.sh import        # load them into the cluster
kubectl apply -k k3s/platform   # once per cluster: cert-manager and KEDA, installed by K3s's Helm controller
kubectl wait --for condition=established crd/certificates.cert-manager.io crd/issuers.cert-manager.io crd/scaledobjects.keda.sh
kubectl apply -k k3s/overlays/local
k3s/scripts/env-to-secrets.sh   # the compose .env files as Secrets (pods wait for them; run it again after a change)
bash tests/k3s-render.test.sh   # every overlay renders and validates (OJ_DOCKER_CONTEXT=desktop-linux on a Mac)
bash tests/k3s-pki.test.sh      # certificates.yaml is what k3s/scripts/gen-certificates.sh makes from pki/identities.txt
scripts/k3d-up.sh down
```

The compose stack keeps 80, 443 and 9000, so both can run at once; `K3D_HTTPS_PORT` and `K3D_HTTP_PORT` change the
cluster's host ports (the script stops, naming the holder, when one is taken).

## Certificates

cert-manager signs one Certificate per identity of `pki/identities.txt` (`k3s/base/pki/certificates.yaml`, generated by
`k3s/scripts/gen-certificates.sh`; the CN, SANs, usages and PKCS8 key are those `pki/pki.sh` issues) and keeps each in the
Secret `tls-<identity>` (keys `tls.crt`, `tls.key`, `ca.crt`). A renewal happens 30 days ahead and makes a new key; a deleted
Secret is issued again within seconds. The signing CA is the Secret `oj-ca`:

- locally (`overlays/local`) cert-manager makes a throwaway root; to trust it in a browser:
  `kubectl -n oj get secret oj-ca -o jsonpath='{.data.tls\.crt}' | base64 -d > oj-local-ca.crt`
- on the server, `k3s/scripts/ca-from-pki.sh` loads the compose stack's CA (`pki/out/ca`) before the first apply, so
  everything that already trusts that CA keeps working through the cutover.

Traefik presents the identity `edge` (CN=edge) to the gateway and the portal, as Caddy does, so their allow-lists and the
gateway's client-address rule stay as they are.

## The data layer (`base/data`)

Three Postgres (identity-db, problem-db, submission-db), Kafka, Redis and MinIO are StatefulSets with a PVC each on the
`local-path` class, the same TLS-with-client-certificates as compose. `tests/k3s-data.test.sh` compares Kafka's environment
and the Postgres, Redis and MinIO command lines with `docker-compose.yml` value for value, so the two cannot drift before the
cutover. `postgres.yaml` and `init-scripts.yaml` are generated (`python3 k3s/scripts/gen_data.py postgres|init-scripts`) from
what compose runs and from `kafka/` and `minio/`; the test fails when a committed file differs.

- **Kafka is capped**: heap `-Xmx512M -Xms512M`, 512Mi requested, 1Gi limit.
- **Secrets**: `k3s/scripts/env-to-secrets.sh` turns the `.env*` files into the Secrets the pods read (`--dry-run` lists names and
  keys). MinIO's root account goes only to MinIO and `minio-init`.
- **Init Jobs** `kafka-init` (ACLs, `kafka/acls.sh`) and `minio-init` (bucket, policies, users) retry until their service
  answers and are removed ten minutes after they finish, so the next `kubectl apply` runs them again. To run one sooner, or
  after changing its script, delete it first (`kubectl -n oj delete job kafka-init minio-init`): a Job's spec cannot change.
- **Every pod is non-root** with the `RuntimeDefault` seccomp profile and no capabilities, so the namespace's `restricted` Pod
  Security warning stays quiet. A volume first written as root (an earlier version of the pod) must be deleted, not reused.
- `enableServiceLinks: false` everywhere: a Service named `kafka` would put `KAFKA_PORT` into Kafka's environment, and the broker
  reads every `KAFKA_*` variable as configuration. Service `kafka` also publishes not-ready addresses: the broker's controller
  quorum voter is `kafka:9093` and it is not Ready until it has joined.

## Services, edge and network (`base/services`, `base/edge`, `base/network`)

identity-service, problem-service, submission-service and api-gateway (`services/java.yaml`, generated by
`k3s/scripts/gen_services.py java`), the portal and Jaeger are Deployments over mutual TLS with the identity's own certificate.
`tests/k3s-services.test.sh` compares each service's environment with `docker-compose.yml`'s, the generated files with their
generators, and Traefik's headers and body limits with `edge/Caddyfile`'s. Differences from compose, on purpose:

- The JVMs get `-XX:MaxRAMPercentage=50.0 -XX:+UseSerialGC` and a memory limit (1Gi, the gateway 768Mi); a JVM start is CPU-bound,
  so each asks for 250m of CPU.
- A read-only root filesystem with `/tmp` as an emptyDir; non-root, `RuntimeDefault` seccomp, no capabilities, everywhere.
- The portal's nginx (uid 101) binds 443: the pod sets the safe sysctl `net.ipv4.ip_unprivileged_port_start=0` that Docker
  sets for a container.
- submission-service is replaced (`Recreate`), not rolled: its pending runs live in its memory.
- Traefik is the edge. It presents the identity `edge` (CN=edge) to the gateway and the portal, as Caddy does; `http` redirects to
  `https`; `/api/v1/problems` may carry 56 MiB, the rest of `/api` 1 MB. The browser-facing certificate is the Secret `edge-tls`:
  `overlays/local` signs one for `localhost` with its throwaway CA; the server's is Let's Encrypt (Task 10).
- **NetworkPolicies**: ingress is denied unless a policy allows it (`network/policies.yaml`): each store is reached by its own
  service, the services by the gateway, the gateway and the portal by Traefik. The test fails when a Service port has no allow
  rule (the actuators' 8081, for Prometheus, come with the observability task).
- The consoles are not Services: `kubectl -n oj port-forward pod/minio-0 9001`, `kubectl -n oj port-forward deploy/jaeger 16686`.

Locally the images are the ones `scripts/local-stack.sh build` made, loaded by `scripts/k3d-up.sh import`. Trust the local CA
with `kubectl -n oj get secret oj-ca -o jsonpath='{.data.tls\.crt}' | base64 -d > oj-local-ca.crt` and use it as
`curl --cacert oj-local-ca.crt https://localhost:18443/api/v1/languages`.

## The Judge Pod and the Run Pod (`base/judge`)

`judge` and `run-judge` (`judge/judge.yaml`, generated by `k3s/scripts/gen_services.py judge`) pair a sandbox with a worker, one to
one: the worker consumes `submission.requested` (the run pod `run.requested`), calls its own sandbox on `localhost:8080` over mutual
TLS and publishes the verdict. KEDA will scale the Deployments (task 7); a new pod is a new pair, so the sandbox never gets more
than the one request its worker sends. `tests/k3s-judge.test.sh` compares the worker's environment and the sandbox's hardening with
compose's.

- **The sandbox is a native sidecar** (an init container with `restartPolicy: Always`): it starts before the worker, which waits for
  its startup probe (compose's `depends_on: service_healthy`), and stops after it, so a judgement in flight keeps its sandbox through
  the 120 s the worker has to finish after SIGTERM.
- **Hardening is compose's `x-sandbox`**: not privileged, every capability dropped but `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETGID`,
  `SETUID`, `KILL`, no privilege escalation, a read-only root with `/judger` and `/tmp` memory-backed, the pinned image digest.
  gunicorn runs as root, as in the image; the run users (12001-12003) cannot read the 0440 TLS directory.
- **What a pod cannot do that compose's `sandbox-net` did.** The containers of a pod share one network namespace, so the
  contestant's code is on the worker's network. The pod therefore has no ServiceAccount token, the sandbox container does not get
  the worker's certificate (Kafka, MinIO and the services all need a client certificate), and a NetworkPolicy (`egress-judge`,
  `egress-run-judge`) lets the pod reach only Kafka, MinIO (judge), submission-service (judge), Jaeger and DNS: no database, no other
  service, no internet, no node. Java and Go submissions have no seccomp filter (see the README's open item), which makes this the
  boundary that matters for them.
- **Audit trail**: `POD_NAME` (Downward API) is the worker's name, so `t_submissions.judged_by` and the registry's hostname (the
  sandbox shares the pod's hostname) are the pod that judged.
- Locally the sandbox is the mock (`overlays/local/mock-sandbox.yaml`). A pod-wide process limit is the kubelet's:
  `scripts/k3d-up.sh` sets `pod-max-pids=2048` (compose gave the sandbox 1024); install K3s on the server with
  `--kubelet-arg=pod-max-pids=2048`. A cluster created before that flag needs `scripts/k3d-up.sh down` and `up`.

## Autoscaling (`base/keda`, `platform/keda.yaml`)

KEDA scales `judge` (1 to 4 pods) and `run-judge` (1 to 2) with the Kafka lag of their consumer groups: one more pod per 5 records
waiting on `submission.requested` (per 3 on `run.requested`). Never to zero (the heartbeat relay and a warm sandbox need a pod). KEDA's
`cooldownPeriod` only covers the step down to zero, so the five minutes a pod stays after the load is gone are the HPA's
`scaleDown.stabilizationWindowSeconds: 300`. The Deployments set no `replicas`, so a later `kubectl apply` does not reset the count.

- KEDA reads Kafka as its own identity (`keda`, certificate `tls-keda`), which `kafka/acls.sh` lets describe those two groups and topics
  and nothing else. It runs in its own namespace, and the broker advertises itself as `kafka:29092` (as in compose), so
  `platform/keda-namespace.yaml` makes `kafka` resolve there too (an ExternalName alias) and Kafka's NetworkPolicy admits that namespace.
- **The node's memory is the real ceiling.** The scheduler places a pod by its `requests`: a judge pod asks for 1664Mi (sandbox 1536Mi +
  worker 128Mi), the rest of the stack for about 3.6Gi. So `maxReplicaCount` of both Deployments together must not exceed
  `(allocatable memory - 3.6Gi) / 1.66Gi`; past that the HPA asks for more pods than fit and the extra ones stay Pending (on the 10Gi
  k3d node three judge pods and one run pod fit, the fourth judge pod waits), never an out-of-memory kill.
- Trying it: `TRIGGER_SLOW` in a source makes the mock take three seconds (`MOCK_SLOW_SECONDS`), so records published to
  `submission.requested` build a lag. `kafka-console-producer.sh` in `kafka-0` (the plaintext loopback listener) can publish copies of an
  outbox record (`SELECT convert_from(payload, 'UTF8') FROM t_outbox WHERE topic = 'submission.requested'`) with fresh `submissionId`s.

## Observability (`base/observability`)

Prometheus, Alertmanager, Grafana, kube-state-metrics and the three postgres-exporters, the Redis exporter and the Kafka exporter, run
from the compose stack's own files: `config.yaml` (generated by `k3s/scripts/gen_observability.py`) holds `prometheus.yml`,
`alerts.yml`, `alertmanager/` and `grafana/` byte for byte, apart from the jobs below, so the two stacks cannot drift. The
Service names are compose's, so every static scrape job is unchanged.

- **The judge pods are found through the Kubernetes API** (`kubernetes_sd_configs`, role `pod`, label `app=judge` / `app=run-judge`,
  job names `judge-worker` / `run-worker` as before, one target per pod on 9100, labelled `pod`). A pod KEDA adds is scraped at once; a
  deleted one drops out, so `JudgeWorkerDown` / `RunWorkerDown` (`absent(up{...} == 1)`) are unchanged: they ask whether any is still up.
- **`JudgePodOOMKilled`** (from kube-state-metrics, which watches pods in `oj` through a namespaced read-only Role): a `sandbox` or
  `worker` container restarted in the last 10 minutes and was OOM-killed. The reason stays on the series for the pod's life, so the
  restart counter says the kill is recent. The alert is in `alerts.yml`, so it is also loaded in compose, where it never fires.
- **Not part of this base:** node-exporter and cAdvisor read the host (`hostPath`, `hostPID`), which Pod Security `baseline` forbids in
  `oj`, and cAdvisor's labels on Kubernetes are `pod` / `container`, not compose's `name`. So `HostDiskAlmostFull` and
  `ContainerMemoryNearLimit` and the Infrastructure dashboard's host and container panels have no data on K3s. Follow-up for the server:
  node-exporter in its own privileged namespace, and the kubelet's cAdvisor (`/metrics/cadvisor`) scraped through the API server.
- Prometheus and kube-state-metrics are the only pods with a ServiceAccount token (each its own Role, no ClusterRole). Everything is
  admitted by a NetworkPolicy of `policies.yaml` (Prometheus to what it scrapes, Grafana to Prometheus, each exporter to the one thing it
  reads); the exporters' ports answer only a client certificate, so their probes are TCP, which shows as a `TLS handshake error ... EOF` line in
  their logs every few seconds.
- Secrets (`env-to-secrets.sh`): `pg-monitor`, `grafana-admin` and the optional `alertmanager-telegram` (empty without the two
  variables in `.env`: Alertmanager then shows alerts only in its UI). **Once per database**, `k3s/scripts/pg-monitor.sh` creates the
  `oj_monitor` role the postgres-exporters log in with (compose's `migrations/sp12-pg-monitor.sh` for pods); it lives in the database's volume.
- Reaching them: `kubectl -n oj port-forward svc/prometheus 9090:9090` (and `svc/grafana 3000:3000`, `svc/alertmanager 9093:9093`).
  Grafana's login is `admin` and the password in the Secret `grafana-admin`. Prometheus reads its ConfigMap at start:
  `kubectl -n oj rollout restart deploy/prometheus` after a change.
- Trying `JudgePodOOMKilled` without the sandbox: a throwaway pod in `oj` with a container named `sandbox` and a memory limit it exceeds
  (`python -c "b=bytearray(200*1024*1024)"` under `limits.memory: 48Mi`) restarts as OOMKilled and the alert fires within two minutes.

## Backup and restore (`base/backup`, `k3s/backup/`)

A CronJob `backup` runs at 03:00 (Asia/Ho_Chi_Minh, as `backup/systemd/oj-backup.timer`): `dump` writes the three Postgres dumps and the
row counts before and after each (`pg_dump -Fc` over TLS with the identity `backup`, as each database's owner), `mirror` copies the
test-case bucket and counts its objects, `restic` snapshots the staging directory (`/staging`) and applies compose's retention (7 daily, 4
weekly, 6 monthly). One of them failing stops the night: a snapshot is only taken of a complete staging directory, and the next night is the
retry. The scripts are `k3s/backup/*.sh` (shellchecked), carried into the ConfigMap by `k3s/scripts/gen_backup.py`.

- **The repository is off the cluster's disk by design.** The base names none: `RESTIC_REPOSITORY`, `RESTIC_PASSWORD` and, for S3 or B2,
  their keys come from `.env` through `env-to-secrets.sh` into the Secret `restic` (see `.env.example`). Without a repository and a password
  the job stops with a message instead of skipping the night. Keep a copy of the password elsewhere: without it the snapshots are unreadable.
  On k3d, `scripts/local-stack.sh init` sets `RESTIC_REPOSITORY=/repo` and the local overlay mounts the claim `restic-repo` there.
- **What the snapshot holds:** the data (three dumps, the bucket). Not the Secrets: `.env*` and `pki/out` (the CA key) live on the host, and
  compose's `backup/backup.sh` snapshot of them stops when compose does, so after the cutover put them in the same repository by hand
  (`restic backup --host oj .env* pki/out` with the repository's variables) and again after each change.
- **The restore drill:** `k3s/scripts/restore-drill.sh` runs the suspended CronJob `restore-drill`: the latest snapshot into a throwaway
  Postgres inside one pod (no network, no certificate, no service credential), and the row counts compared with those taken at backup time
  by `backup/lib.sh`'s `compare_counts`, the function compose's drill uses. Exit 0 and only PASS (or INFO) lines means the backup restores;
  a snapshot older than 36 hours, a wrong password or a missing repository fails it. Run it after the first backup and now and then.
- The first connection of a freshly started pod can be refused until the node has programmed the network policy that admits it, so `dump.sh`
  and `mirror.sh` wait up to a minute for their targets instead of failing the night.

## Cutover from compose (task 10, on the server)

The order keeps compose whole until the last step, so every step before the DNS change can be undone by doing nothing:

1. **Install K3s** with `--kubelet-arg=pod-max-pids=2048`, then `kubectl apply -k k3s/platform`, wait for the CRDs (see the top of this
   file), and make the secrets: copy the `.env*` files and `pki/out` to the machine that runs kubectl, `k3s/scripts/ca-from-pki.sh` (the
   Secret `oj-ca`, so the leaves keep the CA the clients already trust), `k3s/scripts/env-to-secrets.sh`.
2. **Apply `overlays/vps` up to the data layer and the services** (no judge pods and no KEDA yet: the judge Deployments are applied last
   in step 5). Set `RESTIC_REPOSITORY` and `RESTIC_PASSWORD` (off-host) first, and `k3s/scripts/pg-monitor.sh` once the databases are up.
3. **Copy the data, with the services stopped on K3s** (`kubectl -n oj scale deploy/identity-service deploy/problem-service
   deploy/submission-service deploy/api-gateway --replicas=0`). Each database streams from compose into its pod, rehearsed from the compose
   stack into k3d (the dump carries Flyway's history, so the services start without migrating):

       docker --context default exec oj-identity-db sh -c 'pg_dump -Fc --no-owner -U "$POSTGRES_USER" "$POSTGRES_DB"' \
         | kubectl -n oj exec -i identity-db-0 -- sh -c 'pg_restore --clean --if-exists --no-owner --exit-on-error -U "$POSTGRES_USER" -d "$POSTGRES_DB"'

   and the same for `problem` and `submission`. The test-case bucket: `mc mirror` inside `oj-minio` into a directory, `docker cp` it out,
   `kubectl -n oj port-forward svc/minio 19000:9000`, then the MinIO image's `mc` from a container
   (`docker run --rm --entrypoint mc -v <dir>:/in:ro -e MC_HOST_k3s=https://<root>:<password>@<host>:19000 <minio image> --insecure
   mirror --overwrite --remove /in k3s/test-cases`; `--remove` makes it an exact copy; the root account is in the Secret `minio-root`).
   Scale the services back up and let them become ready.
4. **Read-only smoke test with a temporary DNS** (`/etc/hosts` on your machine pointing the public name at the server): log in, list problems,
   open a problem page, read a submission. Run `k3s/scripts/restore-drill.sh` after the first `kubectl create job --from=cronjob/backup`.
5. **Stop compose accepting submissions** (`docker compose stop api-gateway`), wait until `oj_queue_depth` and the consumer lag are 0, dump
   `submission-db` again and copy it as in step 3, then apply the judge Deployments and KEDA (`kubectl apply -k k3s/overlays/vps` in full)
   and change the DNS to the server. Compose's Caddy and K3s's Traefik both want 80/443: stop compose's `edge` first, or run K3s on the
   other IP until this step.
6. **Write smoke test:** submit, watch the SSE stream deliver the verdict, `scripts/stats-check.sh` (it reads compose's containers: against
   K3s use its two queries through `kubectl exec`) must PASS, a Jaeger trace must span the pods, `judged_by` names a judge pod.
7. **Observe for 24 hours** (Prometheus targets all up, no alert but `DefaultAdminPassword` if the seed password is still in use), then
   `docker compose down` keeping the volumes for seven days, and write the date here. **Rollback until then:** point the DNS back and
   `docker compose up -d`: compose's data was never touched, only copied (rows written on K3s since the cutover are lost).

Task 10 has not been done: everything above the DNS change is rehearsed here only as far as it can be (the Postgres stream and the MinIO
copy from the compose stack into k3d, the backup and the drill), and Let's Encrypt for `edge-tls` is not in `overlays/vps` yet.

## What cannot be done on a laptop

The real qduoj sandbox is amd64 and needs the Linux host's kernel, so locally the Judge Pod runs the mock. Left for the
server (the checklist grows as the plan's tasks land):

- Task 6, sizing the sandbox's memory and CPU (and checking that the memory-backed `/judger` volume allows `exec`, that the six capabilities
  are enough under `RuntimeDefault` seccomp and that a C++ compile fits the memory limit) with real judgements (a+b, a heavy compile, a time-limit overrun, an
  out-of-memory kill, `kubectl delete pod` in the middle of a 10 s C++ judgement).
- Task 10, the cutover from compose.
